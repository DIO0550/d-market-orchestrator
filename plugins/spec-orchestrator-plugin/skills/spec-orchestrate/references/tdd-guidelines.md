# t-wada TDD ガイドライン

テストを含む実装計画を作成する際、t-wada 氏の TDD（テスト駆動開発）手法に基づいてタスクと設計を構成する。

## 基本原則

### 1. TODOリスト駆動

実装を始める前に、テストケースをTODOリストとして洗い出す。
このリストが実装の「地図」となり、何をどの順番で作るかを決定する。

```
テストTODOリスト:
- [ ] 正常系: 有効な入力で期待する結果を返す
- [ ] 正常系: 境界値で正しく動作する
- [ ] 異常系: 無効な入力でエラーを返す
- [ ] 異常系: null/undefined の扱い
- [ ] エッジケース: 空文字列
- [ ] エッジケース: 最大長を超える入力
```

### 2. Red-Green-Refactor サイクル

各テストケースに対して、以下のサイクルを繰り返す:

```
RED    → テストを書く（失敗することを確認）
GREEN  → テストを通す最小限の実装を書く
REFACTOR → コードを改善する（テストが通ったまま）
```

### 3. 実装戦略の使い分け

テストを通す（GREEN）段階で、状況に応じて3つの戦略を使い分ける:

- **仮実装（Fake It）**: ハードコードされた値を返して、まずテストを通す。その後のテストで一般化を強制する
- **三角測量（Triangulation）**: 2つ以上のテストケースから一般的なアルゴリズムを導き出す
- **明白な実装（Obvious Implementation）**: 実装が自明な場合は直接書く

## タスク構成パターン

テストを含む場合、tasks.md の実装グループ（`## T{n}`）を TDD サイクルで構成する。

### 構成ルール

1. テストTODOリストは `test-cases.md` のケース一覧として作る
2. 実装グループ（`## T{n}`）を機能単位に分割し、各単位を Red → Green → Refactor の順で並べる
3. 機能単位は小さく保つ（1つの振る舞い = 1つの TDD サイクル）
4. 先に書くテストが後のテストの土台となるよう、シンプルなケースから始める

### タスク順序の原則

```
正常系（最もシンプルなケース）
  ↓
正常系（バリエーション追加）
  ↓
境界値
  ↓
異常系・エッジケース
  ↓
リファクタリング（横断的な改善）
```

## 検証計画への反映

implementation-plan.md の検証計画セクションと test-cases.md で、TDD で作成されるテストの全体像を記載する:

- テストファイルの配置場所
- テストの分類（単体 / 結合 / E2E）
- テストTODOリスト（実装時にそのまま使えるレベルの粒度）
- テスト実行コマンド
