# 作業の種類（feature / bugfix / refactor）

`goal.md` の `**種類**:` で決まる。種類ごとの手順は下の節が各フェーズに**足す**。書いていないフェーズは各フェーズのファイルのまま。

| 種類 | 足す手順 |
|---|---|
| `feature` | 無し |
| `bugfix` | 再現テストを先にコミットしてから直す（「bugfix」） |
| `refactor` | 現状を固定するテストを先にコミットし、既存のテストを書き換えない（「refactor」） |

## 決め方

- 依頼の Issue に `flow:feature` / `flow:bugfix` / `flow:refactor` のラベルがあれば、planner はそれを案に書く。無ければ依頼から案を書き、根拠を返す
- **決めるのはユーザー。** フェーズ 2 の目標確定で `goal.md` と一緒に確定する。planner と指示役は提案までで、「無ければ feature」のような既定値も置かない（選ぶ側と、手順が軽くなって得をする側が同じだと軽い側へ倒れ、バグ修正の再現テストが抜ける）
- **検証を軽くする種類は作らない。** どの種類も計画レビューとループの検証を省かない
- 確定後に種類が合わないと分かったら（バグだと思ったら仕様の変更だった、等）、エスカレーション条件 A
- ソースを変えない調査は、このハーネスの出力（コミットと PR）に合わないので種類に無い

## 2 つの工程に分ける（bugfix / refactor のループ 1 回目）

implementer はコミットしないので、1 回の呼び出しで書かせると「テストだけが先に入ったコミット」が作れない。ループ 1 回目の 3-1 を 2 つの工程に分けて implementer を起動する（どちらも新しい Agent 呼び出し）。

1. **第 1 工程**（bugfix は `工程: 再現テスト`、refactor は `工程: 現状の固定`）: 計画の第 1 工程のテストだけを書かせる。返ってきたら 3-1 の `git status --porcelain` の突き合わせを、計画の第 1 工程のテストのファイルだけに狭める。種類の節の「第 1 工程の確かめ方」で合格したらコミットする（`loop 1: 再現テスト` など）。これが**第 1 工程のコミット**で、`loop-log.md` の Loop 1 に書く
2. **第 1 工程に書くものが無い**（計画が「無し」とした）なら第 1 工程を省き、`BASE` を第 1 工程のコミットの代わりにする（そのことを Loop 1 に書く）
3. **第 2 工程**（bugfix は `工程: 修正`、refactor は `工程: リファクタ`）: 残りのタスクを実装させる。2 回目以降の回と、PR の前の直しも第 2 工程の値で渡す。**コミットの前に毎回**、種類の節の「第 2 工程以降の確かめ方」を走らせ、外れていたらコミットせずに implementer に戻す

## bugfix: 再現を先に固定してから直す

修正と同時に書いたテストは、修正前のコードで落ちたかが誰にも分からない。直したつもりで別の箇所を直していても通る。

### フェーズ 1（planner）

- `implementation-plan.md` の「背景」に、症状を **再現手順**（どの入力・操作・状態から）・**期待する結果**（拠り所の仕様・既存テスト）・**実際の結果** の 3 つに分けて書く。再現手順が書けないなら目標が決まっていないので、`goal.md` の未解決の確認事項に書く
- 「検証計画」と `tasks.md` の**先頭**に再現テストを置き、置くファイル・テストの名前・走らせる検査コマンド・**修正前のコードで、どの assert がどの値で落ちるか**（期待と実際）を書く
  - **今ある公開 API だけで書く。** 修正で足す API を呼ぶと、修正前は実行時エラーや import の失敗で落ちて assert まで届かない
  - **修正で書き換える既存テストと同じファイルに置かない。** 同じファイルだと、第 2 工程の `git diff --exit-code` が再現テストの書き換えと見分けられない
  - **自動テストで再現できないなら、** その理由と代わりの確かめ方を書き、再現テストを置かない（第 1 工程を省く）
- 期待する結果の拠り所が仕様にも既存のテストにも無いなら、それは仕様の変更で bugfix に合わない。`goal.md` の未解決の確認事項に書く
- `goal.md` の完了条件に、再現テストが通ることを確かめ方付きで入れる

### ループ（指示役）

- **第 1 工程の確かめ方:** 返ってきた検査の結果で、**再現テストだけが落ち、落ち方が計画に書いた assert の失敗であり、ほかの検査は通っている**こと。再現テストが通った・assert 以外（実行時エラー・import の失敗等）で落ちた・ほかのテストも落ちた、のどれかなら再現になっていないので、コミットせずに planner に計画を直させる
- **第 2 工程以降の確かめ方:** `git diff --exit-code <第 1 工程のコミット> -- <再現テストのファイル>` が 0（再現テストを書き換えていない）。再現テストが通ることは goal-checker が完了条件として確かめる
- 第 1 工程を省いたなら、計画の代わりの確かめ方を第 2 工程の implementer に修正の前と後で行わせ、前は症状が出て後は出ないことを返させて Loop 1 に書く

### PR

本文に、**第 1 工程のコミット**（再現テスト）と、それ以降の修正のコミットを並べて書く。読む人が前者だけをチェックアウトして、テストが落ちることを確かめられるようにする。第 1 工程を省いたなら、その理由と代わりの確かめ方の結果を書く。

## refactor: 振る舞いを変えず、既存のテストで確かめる

振る舞いが変わっていない根拠は、**書き換えていない既存のテストだけ**。テストを実装と一緒に書き換えると、緑のままでも振る舞いが変わっていないとは言えなくなる。

### フェーズ 1（planner）

`implementation-plan.md` に次を足す（「影響範囲」「検証計画」の中でよい）。

- **守っている既存テスト** — 触るコードを守っているテストのファイル・走らせるコマンド・件数
- **現状を固定するテスト** — 守っている既存テストが無い範囲に、今のコードで通るテストを先に足す。足すものが無いなら「無し」（第 1 工程を省く）
- **移動表**（移動元 → 移動先）と**改名表**（旧名 → 新名）。無いなら「無し」
- **書き換えない範囲** — テストとその共有物（ヘルパー・フィクスチャ・スナップショット・テストのセットアップ）の pathspec と、テストを走らせる**配線**（テストの対象を決める設定・テストを読み込む宣言）の場所。配線を消すと、テストを書き換えずに走らなくできる
- 仕様の変更や既存テストの書き換えが要ると分かったら refactor に合わない。`goal.md` の未解決の確認事項に書く

書き換えない範囲で**してよいこと**（これ以外はしない）:

- テストを足す
- 移動表にあるファイルを移動する。移動に伴う中身の変更は、下の 2 つに当たるものに限る
- 参照先（import のパス等）を、移動表にある移動先へ書き換える。同じものを指したまま場所だけが変わる書き換えに限る
- 改名表にある名前を書き換える。表に無い名前を変えると、別の実装への向け替えが改名に紛れて読めなくなる

**しないこと**: assert を含むテストの本文（期待値・入力・テストの名前）を変える / テストを消す・skip する / 配線を消す（移動表にある移動の片割れを除く）/ 参照先を別の実装・スタブへ向け替える / スナップショット・期待値のファイルを更新して通す

### ループ（指示役）

- **第 1 工程の確かめ方:** 足したテストを含め、検査がすべて今のコードのまま通る
- **第 2 工程以降の確かめ方:** `git diff <第 1 工程のコミット> -- <書き換えない範囲と配線の場所>` を読み、「してよいこと」に当たらない行があれば、その行を指摘として implementer に戻す（指示役が読むソースの差分はこの範囲だけ）
- テストが足りないという指摘には、既存のテストを書き換えず新しいテストを足して応えさせる
- `test-reviewer` は省かない。振る舞いが変わっていない根拠は既存のテストだけなので、それが実装を守っているかを実測する役が要る
