# 作業の種類（feature / bugfix / refactor）

`goal.md` の `**種類**:` で決まる。種類ごとの手順は下の節が各フェーズに**足す**。書いていないフェーズは各フェーズのファイルのまま。

| 種類 | 足す手順 |
|---|---|
| `feature` | assert で落ちるテストと骨組みを先にコミットし、RED を確かめてから実装する（「feature」） |
| `bugfix` | 再現テストを先にコミットしてから直す（「bugfix」） |
| `refactor` | 現状を固定するテストを先にコミットし、既存のテストを書き換えない（「refactor」） |

## 決め方

- 依頼の Issue に `flow:feature` / `flow:bugfix` / `flow:refactor` のラベルがあれば、planner はそれを案に書く。無ければ依頼から案を書き、根拠を返す
- **決めるのはユーザー。** フェーズ 2 の目標確定で `goal.md` と一緒に確定する。planner と指示役は提案までで、「無ければ feature」のような既定値も置かない（選ぶ側と、手順が軽くなって得をする側が同じだと軽い側へ倒れ、バグ修正の再現テストが抜ける）
- **検証を軽くする種類は作らない。** どの種類も計画レビューとループの検証を省かない
- 確定後に種類が合わないと分かったら（バグだと思ったら仕様の変更だった、等）、エスカレーション条件 A
- ソースを変えない調査は、このハーネスの出力（コミットと PR）に合わないので種類に無い

## 2 つの工程に分ける（ループ 1 回目）

implementer はコミットしないので、1 回の呼び出しで書かせると「第 1 工程の分だけが先に入ったコミット」が作れない。ループ 1 回目の 3-1 を 2 つの工程に分けて implementer を起動する（どちらも新しい Agent 呼び出し）。

| 種類 | 第 1 工程（`工程:` の値） | 第 1 工程に書くもの | 第 2 工程（`工程:` の値） |
|---|---|---|---|
| `feature` | `仕様の固定` | テストと骨組み | `仕様の実現` |
| `bugfix` | `再現テスト` | 再現テスト | `修正` |
| `refactor` | `現状の固定` | 現状を固定するテスト | `リファクタ` |

1. **第 1 工程**: 計画で第 1 工程に挙げたものだけを書かせる。返ってきたら 3-1 の `git status --porcelain` の突き合わせを、計画で第 1 工程に挙げたファイルだけに狭める。種類の節の「第 1 工程の確かめ方」で合格したらコミットする（`loop 1: 再現テスト` など）。これが**第 1 工程のコミット**で、`loop-log.md` の Loop 1 に書く
2. **第 1 工程に書くものが無い**（計画が「無し」とした、または省く条件に当たるとした）なら第 1 工程を省き、`BASE` を第 1 工程のコミットの代わりにする（そのことを Loop 1 に書く）
3. **第 2 工程**: 残りのタスクを実装させる。2 回目以降の回と、PR の前の直しも第 2 工程の値で渡す。**コミットの前に毎回**、種類の節の「第 2 工程以降の確かめ方」を走らせ、外れていたらコミットせずに implementer に戻す
   - `feature` / `bugfix` は、ループ 1 回目の第 2 工程から返ったら、まず次の終了コードが 0（第 1 工程のテストを書き換えていない）であることを確かめる。2 回目以降と PR の前の直しで何を確かめるかは種類の節に従う（bugfix は同じコマンドを毎回、feature はテストの追加を認める）

     ```bash
     git diff --exit-code <第 1 工程のコミット> -- <第 1 工程のテストのファイル>
     ```

## feature: 仕様を落ちるテストで固定してから実現する

実装と同時に書いたテストは、実装に合わせて書かれていないかを確かめられない。`test-reviewer` が示すのは判断ごとにテストが落ちるかで、テストが仕様から先に書かれたかではない。

### フェーズ 1（planner）

- `implementation-plan.md` の「検証計画」に**第 1 工程のファイル**を列挙し、`tasks.md` の Implementation は第 1 工程のタスク → 第 2 工程のタスクの順に並べて、各行の頭に `[仕様の固定]` / `[仕様の実現]` を付ける。第 1 工程に置くのは次のもの
  - テストと、その共有物（ヘルパー・フィクスチャ）
  - **骨組み**: 第 1 工程で足す公開 API のシグネチャと仮の戻り値。新しい関数・型に足すフィールド・直和に足す枝（状態遷移なら状態をそのまま返す）を含む。テストだけだと、新しい API を呼ぶテストは型エラー・import の失敗・実行時エラーで落ちて assert まで届かない
  - 型・コンパイルを通すために要る呼び出し側の機械的な書き換え（本番コードと既存テストの呼び出し側。「影響範囲」で数えたもの）
  - テストを走らせる配線を新しく足すなら、その配線
- 既存テストの期待値を変えるなら、第 1 工程で書き換えて RED に数える
- 第 2 工程に置くのは実装
- **RED 表**: 別の表ではなく、「検証計画」のテストケース表に列を足したもの。各行に テスト名 / 骨組みの仮の戻り値 / 期待結果 / 第 1 工程での結果（RED か、骨組みのままで通るか）/ 予想する失敗の 1 行目 を書く。行は第 2 工程で通す順（単純なものから。`tdd-guidelines.md` の順序）に並べる。三角測量（同じ公開 API に別の入力で足すテスト）もここに載せる
- **予想する失敗の 1 行目として書けるのは、assert の失敗だけ**: テストフレームワークの assert の失敗（vitest / jest の `AssertionError`、pytest の `assert` の失敗、`cargo test` の ``assertion `left == right` failed`` など）と、RED 表で予告した unwrap 等の失敗。型エラー・`TypeError` などの実行時エラー・モジュールが見つからない（ファイル単位の失敗）・コンパイルエラー・未実装の印（`todo!()` / `NotImplementedError` など）は assert に届いていないので書けない。このプロジェクトで認める形を、検査コマンドの実際の出力の綴りで「検証計画」に書く
- **確かめ方のコマンド**も「検証計画」に書き、`mktemp -d` の中などで走らせて出力の形を確かめておく
  - 第 1 工程用: 落ちたテストの名前と失敗の 1 行目を並べるコマンド（テストランナーに JSON などの機械向けの出力があればそれを使う）
  - 第 2 工程用: テストを 1 件だけ走らせるコマンドと、走った件数が 1 であることの確かめ方（名前の照合が外れると 0 件のまま終了コード 0 になり、「先に通った」と取り違える）
- **仮の戻り値の作り方**
  - 期待結果と違う値を選ぶ（期待と同じ値だと、規則を丸ごと壊しても通る）
  - 成功側（`Ok` / `Some` など）で期待と違う値を作れるならそちらにする（assert まで届く）
  - ドメインの値は既存の生成関数やフィクスチャで作る。型の強制変換（`as` など）で作らない
  - 作れないときだけ失敗側（`Err` / `None` など）を返し、RED 表に unwrap 等の失敗を、どの呼び出しで起きるかと一緒に予告する
  - 例外を投げる・未実装の印を置く形にしない（assert の失敗と見分けられない）
  - 使わない引数の書き方・doc など、プロジェクトの lint が骨組みにも掛けるものは満たす
- 骨組みのままで通るテストは理由を付けて RED 表に載せる。同じ公開 API に RED のテストが 1 件以上あるときだけ認める
- 型だけを確かめるテスト（型テスト）は RED の対象外（シグネチャ自体が骨組みで、第 1 工程の型検査で通る）
- **第 1 工程を省く条件:** 自動テストで落とせるものが無い（doc・設定だけ、テストを持たないスクリプト、位置・大きさだけの見た目）。省くなら理由と代わりの確かめ方を書く。一部だけ当たるなら、その部分を第 1 工程に置かず理由を書く
- 既存の振る舞いの誤りを直す作業（期待する結果の拠り所が既存の仕様・テストにある）は bugfix、振る舞いを変えない作業は refactor で、feature に合わない。`goal.md` の未解決の確認事項に書く

### ループ（指示役）

- **第 1 工程の確かめ方:** 指示役がコミットの前に、計画に書いた第 1 工程用のコマンドを**自分で**走らせ、出力を RED 表と突き合わせる。implementer の申告ではなく、指示役が取ったこの出力が RED の拠り所になる
  - 落ちたテストの集合が、RED 表で RED としたテストの集合と一致する
  - 各テストの失敗の 1 行目が、計画に書いた認める形に入る。予告した unwrap 等は、予告した呼び出しで起きている
  - ファイル単位の失敗（import の失敗など）が無く、テスト以外の検査（lint・型検査など）は通る
  - 外れたら、コミットせずに planner に計画を直させる。合格したら出力を Loop 1 に残してコミットする
- **第 2 工程（`仕様の実現`）で implementer にさせること:** RED 表の順に 1 件ずつ回す
  1. そのテストだけを走らせて、落ちることと、走ったのがちょうど 1 件であることを確かめ、失敗の 1 行目を控える。実装の前に既に通っていたら「先に通った」と控える
  2. 通る最小の実装を書き、同じコマンドで通ることを確かめて次へ進む

  サイクルごとのテスト名・実装前の失敗の 1 行目（または「先に通った」）・通ったことを返させる。第 1 工程のテストと骨組みのシグネチャは変えさせない（変える必要が出たら止めて返させる）。ループ 1 回目の第 2 工程でテストを足すのも計画外
- **第 2 工程以降の確かめ方（ループ 1 回目）:**
  - (a) 「2 つの工程に分ける」の `git diff --exit-code` が 0
  - (b) `git diff <第 1 工程のコミット> -- <骨組みのファイル>` の削除行（`-` で始まる行）を読み、シグネチャの行が無い（仮の戻り値の行は消えてよい）
  - (c) テスト名の集合が一致する: 「サイクルで RED → GREEN にしたもの」∪「先に通ったもの」＝ RED 表の RED の集合で、過不足も重複も無い
  - (d) 各サイクルの実装前の 1 行目が認める形に入る（値は見ない。前のサイクルで変わるため）
  - (c)(d) は implementer の申告を見るだけで、RED → GREEN を実際に回したかまでは確かめられない。機械的な拠り所は、指示役が自分で出力を取った第 1 工程のコミット
  - 先に通ったテストがあれば Loop 1 に書く
- **第 2 工程以降の確かめ方（2 回目以降と PR の前の直し）:** 指摘に応えてテストを足すのはよい（同じファイルでもよい）。第 1 工程のテストを書き換える・消す・skip するのはしない
  - `git diff --numstat <第 1 工程のコミット> -- <第 1 工程のテストのファイル>` の削除の列（2 列目）がすべて 0
  - 同じ範囲の `git diff` の追加行を読み、まるごと新しいテスト（とその import）であって、既存のテストの本文の中への追加ではない
- 指示役が読むソースの差分は、(b) の削除行と、2 回目以降の第 1 工程のテストのファイルの差分だけ
- 第 1 工程を省いたなら、implementer に `工程: 仕様の実現` を渡し、サイクルの記録は求めない。代わりに計画の代わりの確かめ方を行わせ、その結果を返させて Loop 1 に書く
- `test-reviewer` は省かない

### PR

本文に、**第 1 工程のコミット**（テストと骨組み）と、それ以降のコミットを並べて書く。第 1 工程で指示役が取った出力（落ちたテストと失敗の 1 行目）を添え、マージ後も RED を辿れるようにする。第 1 工程を省いたなら、その理由と代わりの確かめ方の結果を書く。

## bugfix: 再現を先に固定してから直す

修正と同時に書いたテストは、修正前のコードで落ちたかが誰にも分からない。直したつもりで別の箇所を直していても通る。

### フェーズ 1（planner）

- `implementation-plan.md` の「背景」に、症状を **再現手順**（どの入力・操作・状態から）・**期待する結果**（拠り所の仕様・既存テスト）・**実際の結果** の 3 つに分けて書く。再現手順が書けないなら目標が決まっていないので、`goal.md` の未解決の確認事項に書く
- 「検証計画」と `tasks.md` の**先頭**に再現テストを置き、置くファイル・テストの名前・走らせる検査コマンド・**修正前のコードで、どの assert がどの値で落ちるか**（期待と実際）を書く
  - **今ある公開 API だけで書く。** 修正で足す API を呼ぶと、修正前は実行時エラーや import の失敗で落ちて assert まで届かない
  - **修正で書き換える既存テストと同じファイルに置かない。** 同じファイルだと、第 2 工程の `git diff --exit-code` が再現テストの書き換えと見分けられない
  - **自動テストで再現できないなら、** その理由と代わりの確かめ方を書き、再現テストを置かない（第 1 工程を省く）
- 期待する結果の拠り所が仕様にも既存のテストにも無いなら、それは仕様の変更で bugfix に合わない。`goal.md` の未解決の確認事項に書く
- `goal.md` の完了条件に、再現テストが通ることを確かめ方付きで入れる

### ループ（指示役）

- **第 1 工程の確かめ方:** 返ってきた検査の結果で、**再現テストだけが落ち、落ち方が計画に書いた assert の失敗であり、ほかの検査は通っている**こと。再現テストが通った・assert 以外（実行時エラー・import の失敗等）で落ちた・ほかのテストも落ちた、のどれかなら再現になっていないので、コミットせずに planner に計画を直させる
- **第 2 工程以降の確かめ方:** どの回も「2 つの工程に分ける」の `git diff --exit-code` が 0（第 1 工程のテストのファイル = 再現テストのファイル。再現テストを書き換えていない）。再現テストが通ることは goal-checker が完了条件として確かめる
- 第 1 工程を省いたなら、計画の代わりの確かめ方を第 2 工程の implementer に修正の前と後で行わせ、前は症状が出て後は出ないことを返させて Loop 1 に書く

### PR

本文に、**第 1 工程のコミット**（再現テスト）と、それ以降の修正のコミットを並べて書く。読む人が前者だけをチェックアウトして、テストが落ちることを確かめられるようにする。第 1 工程を省いたなら、その理由と代わりの確かめ方の結果を書く。

## refactor: 振る舞いを変えず、既存のテストで確かめる

振る舞いが変わっていない根拠は、**書き換えていない既存のテストだけ**。テストを実装と一緒に書き換えると、緑のままでも振る舞いが変わっていないとは言えなくなる。

### フェーズ 1（planner）

`implementation-plan.md` に次を足す（「影響範囲」「検証計画」の中でよい）。

- **守っている既存テスト** — 触るコードを守っているテストのファイル・走らせるコマンド・件数
- **現状を固定するテスト** — 守っている既存テストが無い範囲に、今のコードで通るテストを先に足す。足すものが無いなら「無し」（第 1 工程を省く）
- **移動表**（移動元 → 移動先）と**改名表**（旧名 → 新名）。無いなら「無し」
- **書き換えない範囲** — テストとその共有物（ヘルパー・フィクスチャ・スナップショット・テストのセットアップ）の pathspec と、テストを走らせる**配線**（テストの対象を決める設定・テストを読み込む宣言）の場所。配線を消すと、テストを書き換えずに走らなくできる
- 仕様の変更や既存テストの書き換えが要ると分かったら refactor に合わない。`goal.md` の未解決の確認事項に書く

書き換えない範囲で**してよいこと**（これ以外はしない）:

- テストを足す
- 移動表にあるファイルを移動する。移動に伴う中身の変更は、下の 2 つに当たるものに限る
- 参照先（import のパス等）を、移動表にある移動先へ書き換える。同じものを指したまま場所だけが変わる書き換えに限る
- 改名表にある名前を書き換える。表に無い名前を変えると、別の実装への向け替えが改名に紛れて読めなくなる

**しないこと**: assert を含むテストの本文（期待値・入力・テストの名前）を変える / テストを消す・skip する / 配線を消す（移動表にある移動の片割れを除く）/ 参照先を別の実装・スタブへ向け替える / スナップショット・期待値のファイルを更新して通す

### ループ（指示役）

- **第 1 工程の確かめ方:** 足したテストを含め、検査がすべて今のコードのまま通る
- **第 2 工程以降の確かめ方:** `git diff <第 1 工程のコミット> -- <書き換えない範囲と配線の場所>` を読み、「してよいこと」に当たらない行があれば、その行を指摘として implementer に戻す（指示役が読むソースの差分はこの範囲だけ）
- テストが足りないという指摘には、既存のテストを書き換えず新しいテストを足して応えさせる
- `test-reviewer` は省かない。振る舞いが変わっていない根拠は既存のテストだけなので、それが実装を守っているかを実測する役が要る
