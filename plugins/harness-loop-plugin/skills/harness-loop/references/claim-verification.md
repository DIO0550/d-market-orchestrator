# 主張を書いたら確かめる

計画（planner）・コメントや doc（implementer）に**事実の主張**を書いたら、書き終えるたびにこの手順で実物と照合する。
design-composer の `claim-verification` スキルを、プロジェクトに依らない形にしたもの。
レビューに出してから直すと出し直しが繰り返されるので、書く時点で確かめる。

## 手順

1. **書いた 1 文が、コード・外部ドキュメント・実行結果について何かを主張しているか確認する。** 選択の理由の説明に留まり、確かめられる事実を主張していないなら対象外
2. 主張しているなら、下の表からいちばん近い行を選び、**「確かめ方」の操作を実際に行う**。「読んで確認できるはず」で済ませない
3. 確かめた結果が主張と食い違っていたら、**主張の側を実物に合わせて直す**
4. 同じ事実を説明する記述が複数箇所にあるなら、すべての箇所を同じタイミングで確かめる（1 箇所だけ直すと食い違いが残る）
5. **構造（条件・呼び出し順・置き場所）を変えたら、向きを逆にして確かめる。** 変更前の条件・名前を指す語で差分全体と周辺を `grep` し、その構造を前提にしていた既存の Why / doc / 件数の記述が崩れていないかを見る。崩れていたら新しい構造に合わせて書き直す（消すだけで済ませない）
6. **置き場所・帰属の理由を書いたら反証する。** 「第 1 引数の型が◯◯だから」のような理由は、置き場所の候補になりうる他の型・モジュールにも同じように成り立ってしまわないかを実際に当てはめる。成り立つなら理由になっていないので、対象だけが持つ性質（生成規則・不変条件・値の意味）を挙げ直す

## 主張の形と確かめ方

| 主張の形 | 例 | 確かめ方 |
|---|---|---|
| 参照先 | 「`X` は `Y` から呼ばれる」「この設定は `Z` が読む」 | 参照先を開く。`grep -rn` で呼び出し側を数える |
| 件数・列挙 | 「呼び出しは 3 箇所」「この 4 つの場合」 | 実際に数え直す。数えたコマンドを計画に残す |
| 不在 | 「同じ処理は他に無い」「この関数は他で使われていない」 | 探した場所とコマンドを書く。名前が違う同じ処理も、公開 API の一覧を開いて探す |
| 挙動 | 「空配列を渡すと空を返す」「このコマンドは失敗しても 0 を返す」 | 小さく再現して動かす（`mktemp -d` の中で） |
| 守られている | 「このテストが守っている」「外すと型エラーになる」 | その箇所を実際に壊して、落ちることを見る。終わったら必ず戻す |
| 外部の仕様 | 「このライブラリはこう振る舞う」「この CLI のこのオプションは」 | 依存しているバージョンのドキュメント・ソース・`--help` を開く。挙動に依存するなら動かす |
| 前提・不変条件 | 「常に◯◯である」「〜のときのみ」 | その前提を書いている doc / コメントを `grep` し、今回の変更が崩さないか確かめる |
